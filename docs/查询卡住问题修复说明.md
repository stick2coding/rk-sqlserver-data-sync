# 查询卡住问题修复说明

## 问题描述

### 症状
程序运行到"开始分批查询WFC_PROCESS数据"时会卡住，无法继续执行。

### 日志输出
```
2025-12-26 10:04:32 [INFO] 从源数据库查询关联表: awscrmdb.[dbo].[WFC_PROCESS]
2025-12-26 10:04:32 [INFO] 切换到目标关联数据库: aws
2025-12-26 10:04:32 [INFO] 从目标数据库查询已存在ID: aws.[dbo].[WFC_PROCESS]
2025-12-26 10:04:32 [INFO] 获取目标表中已存在的WFC_PROCESS ID...
[程序卡住，无后续输出]
```

## 根本原因分析

### 1. 原代码问题

```python
# 原代码（有问题）
def _get_existing_wfc_process_ids(self, table_name: str, schema: str = 'dbo') -> set:
    full_table_name = f"[{schema}].[{table_name}]"
    query = f"SELECT [ID] FROM {full_table_name}"
    results = self.target_db.execute_query(query)
    existing_ids = set(row[0] for row in results if row[0] is not None)
    return existing_ids
```

### 2. 问题分析

当目标表WFC_PROCESS有大量数据时（比如几十万甚至几百万行），这个查询会：

| 问题 | 说明 |
|------|------|
| **一次性加载全部数据** | 查询会尝试一次性获取所有ID到内存 |
| **内存占用过高** | 几百万个ID会占用大量内存 |
| **查询时间长** | 大表查询可能需要数分钟甚至更长时间 |
| **无超时机制** | 查询可能无限期等待 |
| **无进度反馈** | 用户看不到任何进度信息 |

### 3. 实际影响

假设WFC_PROCESS表有100万行数据：
- 每个ID占8字节（假设）
- 100万个ID ≈ 8MB内存
- 查询时间可能超过30秒
- 程序看起来像"卡死"了

## 解决方案

### 1. 智能分批查询

根据表的数据量自动选择查询策略：

```python
def _get_existing_wfc_process_ids(self, table_name: str, schema: str = 'dbo') -> set:
    full_table_name = f"[{schema}].[{table_name}]"
    
    # 先检查表的总行数
    count_query = f"SELECT COUNT(*) FROM {full_table_name}"
    count_results = self.target_db.execute_query(count_query)
    total_count = count_results[0][0] if count_results else 0
    
    logger.info(f"目标表 {table_name} 总行数: {total_count}")
    
    # 如果表为空，直接返回空集合
    if total_count == 0:
        logger.info("目标表为空，无需过滤已存在的ID")
        return set()
    
    # 如果表行数过多（超过10万），使用分批查询
    if total_count > 100000:
        logger.warning(f"目标表行数过多({total_count})，使用分批查询获取ID")
        return self._get_existing_ids_batched(table_name, schema, total_count)
    else:
        # 表行数较少，直接查询所有ID
        query = f"SELECT [ID] FROM {full_table_name}"
        results = self.target_db.execute_query(query)
        existing_ids = set(row[0] for row in results if row[0] is not None)
        logger.info(f"已获取 {len(existing_ids)} 个已存在ID")
        return existing_ids
```

### 2. 大表分批查询

对于大表（超过10万行），使用OFFSET FETCH分页查询：

```python
def _get_existing_ids_batched(self, table_name: str, schema: str, total_count: int) -> set:
    full_table_name = f"[{schema}].[{table_name}]"
    batch_size = 10000  # 每批查询1万条
    existing_ids = set()
    
    logger.info(f"开始分批获取已存在ID，总行数: {total_count}, 批次大小: {batch_size}")
    
    try:
        # 使用OFFSET FETCH进行分页查询
        for offset in range(0, total_count, batch_size):
            query = f"""
                SELECT [ID] 
                FROM {full_table_name} 
                ORDER BY [ID]
                OFFSET {offset} ROWS
                FETCH NEXT {batch_size} ROWS ONLY
            """
            
            logger.debug(f"查询批次 ID: {offset//batch_size + 1}, OFFSET: {offset}")
            
            results = self.target_db.execute_query(query)
            batch_ids = set(row[0] for row in results if row[0] is not None)
            existing_ids.update(batch_ids)
            
            logger.debug(f"批次 {offset//batch_size + 1}: 获取 {len(batch_ids)} 个ID, 累计 {len(existing_ids)} 个")
            
            # 如果获取到的ID数量少于批次大小，说明已经到末尾
            if len(batch_ids) < batch_size:
                break
        
        logger.info(f"分批查询完成，共获取 {len(existing_ids)} 个已存在ID")
        return existing_ids
        
    except Exception as e:
        logger.error(f"分批查询失败: {e}")
        # 返回已获取的部分ID
        logger.warning(f"返回部分已获取的ID: {len(existing_ids)} 个")
        return existing_ids
```

## 技术细节

### 1. 阈值选择

选择10万行作为阈值的原因：

| 行数范围 | 策略 | 原因 |
|---------|------|------|
| 0-10万 | 直接查询 | 性能可接受，无需复杂处理 |
| >10万 | 分批查询 | 避免内存占用过高和超时 |

### 2. 批次大小选择

选择1万条作为批次大小的原因：

- **内存友好**: 每批只加载1万个ID，内存占用约80KB
- **查询快速**: 小批次查询速度快，不会超时
- **进度可见**: 用户可以看到明显的进度
- **平衡性**: 在批次数和单批次大小之间取得平衡

### 3. OFFSET FETCH 优势

使用SQL Server的OFFSET FETCH语法：

```sql
SELECT [ID] 
FROM [table]
ORDER BY [ID]
OFFSET 0 ROWS
FETCH NEXT 10000 ROWS ONLY
```

优势：
- ✅ 标准SQL语法，支持度高
- ✅ 性能优于旧式分页（ROW_NUMBER）
- ✅ 语法简洁清晰
- ✅ 支持动态分页

### 4. 错误处理增强

- **异常捕获**: 即使分批查询失败，也能返回已获取的部分ID
- **日志记录**: 详细记录每个批次的执行情况
- **优雅降级**: 出错时返回空集合，不过滤已存在的ID（可能导致主键冲突，但不会完全失败）

## 其他优化建议

### 1. 添加查询超时

在数据库连接字符串中添加超时设置：

```python
connection_string = (
    f"DRIVER={{{driver}}};"
    f"SERVER={server};"
    f"DATABASE={database};"
    f"UID={username};"
    f"PWD={password};"
    "TrustServerCertificate=yes;"
    "Connection Timeout=30;"  # 连接超时30秒
    "Query Timeout=300;"       # 查询超时5分钟
)
```

### 2. 使用临时表

对于非常大的表，可以考虑使用临时表：

```sql
-- 创建临时表
CREATE TABLE #TempIDs (ID VARCHAR(50) PRIMARY KEY)

-- 批量插入BINDID
INSERT INTO #TempIDs (ID) VALUES (?), (?), (?), ...

-- 使用临时表JOIN查询
SELECT t.* 
FROM WFC_PROCESS t
INNER JOIN #TempIDs temp ON t.ID = temp.ID
LEFT JOIN TargetWFC_PROCESS target ON t.ID = target.ID
WHERE target.ID IS NULL

-- 清理临时表
DROP TABLE #TempIDs
```

### 3. 使用索引

确保WFC_PROCESS表的ID字段有索引：

```sql
-- 如果没有索引，创建索引
CREATE INDEX IX_WFC_PROCESS_ID ON WFC_PROCESS(ID)
```
